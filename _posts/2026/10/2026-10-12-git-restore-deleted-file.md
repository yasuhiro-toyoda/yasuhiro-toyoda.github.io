Gitで管理しているファイルを誤って削除したら、まず**削除をどこまで記録したか**を確認します。未コミットならステージングエリアや直近のコミットから、コミット済みならファイルが残っている過去のコミットから戻せます。**push済みでも復元できます。**

ただし、Gitに保存されていない内容まで戻るとは限りません。この記事では `memo.txt` を例に、状態の確認、復元方法の選択、結果確認の順に進めます。基本操作は [Gitの基本的なコマンド]({% post_url 2026/05/2026-05-06-Gitの基本的なコマンド %}) にまとめています。

## 最初に削除の状態と対象を確認する

WindowsのPowerShellで、対象リポジトリの一番上のフォルダを開きます。次は状態を見るだけのコマンドです。

```powershell
git --version
git status
git status --short -- "memo.txt"
```

`git restore` を使うため、Git 2.23以降が必要です。ここでは、少なくとも一度コミットされた通常のファイルを戻します。一度も記録していない内容については、記事の最後で復元の限界を説明します。

コマンド内の `memo.txt` は実際の対象パスに置き換えます。例えば `"docs/work memo.txt"` のように、空白を含むパスは引用符で囲み、フォルダの区切りは `/` にすると読みやすくなります。`--` は、その後ろが対象ファイルの指定であることを示します。

ここで出てくる保存場所は3つです。

| 保存場所 | この例での意味 |
| --- | --- |
| 作業ツリー | エクスプローラーやエディタで見える、手元のファイル |
| ステージングエリア（インデックス） | `git add` で用意した、次のコミットに含める内容 |
| `HEAD` | 現在のブランチの先端のコミット |

通常の `git status --short` の先頭2文字は、左がステージ済みの変更、右が未ステージの変更です。下の出力例では、空白も意味があります。

```text
 D memo.txt
D  memo.txt
```

上は未ステージの削除、下はステージ済みの削除です。例えば、エクスプローラーで消した直後は上、削除後に `git add` した場合や `git rm` で消した場合は下になります。

| 対象ファイルの状態 | 選ぶ方法 |
| --- | --- |
| ` D`：削除が未ステージ | ステージングエリアから実ファイルを戻す |
| `D `：削除がステージ済み | `HEAD` からステージングエリアと実ファイルを戻す |
| コミット済みで、対象が表示されない | 過去のコミットから1ファイルを取り出し、新しくコミットする |
| 削除コミットをpush済み | 同じ方法で復元して通常のpushをする。コミット全体を打ち消すなら `revert` |

**ファイルが見つからないのに `status` に出ない場合は、削除がコミット済みの可能性があります。** それだけで断定せず、後述の履歴を確認してください。Gitで管理していなかったファイルも、削除後は表示されません。

> **対象を絞って戻す**
>
> 以下は通常のファイル削除の例です。`git status` に競合、merge・rebaseなどの処理中という表示がある場合は、この手順をそのまま実行せず、その処理を先に確認します。復元は対象パスの内容を上書きする操作なので、残したい編集があれば別に保存してください。
{: .callout .callout--caution }

## 未コミット①：削除が未ステージなら実ファイルを戻す

` D memo.txt` の場合は、次を実行します。

```powershell
git restore -- "memo.txt"
Test-Path "memo.txt"
Get-Content "memo.txt"
git status --short -- "memo.txt"
git status --short
```

`Test-Path` が `True` になり、`Get-Content` で内容を確認できます。削除前に他の変更がなければ、対象ファイルは `status` に表示されなくなります。全体の `status` では、別ファイルの変更が残っていることも確認します。

ここでの復元元は、**最後にコミットした内容ではなく、現在のステージングエリア**です。例えば、編集を `git add` してから実ファイルを消した場合は、そのadd済みの内容が戻ります。その場合の表示は `MD` で、復元後も左側の `M`、つまりステージ済みの編集は残ります。

一方、削除前に編集した内容を一度もaddなどで保存していなければ、その新しい編集内容は戻りません。

## 未コミット②：削除がステージ済みなら2か所を戻す

`D  memo.txt` の場合、ステージングエリアにも削除が記録されています。**直近のコミットの内容に戻したい**ときは、復元元と復元先を指定します。

```powershell
git restore --source=HEAD --staged --worktree -- "memo.txt"
Test-Path "memo.txt"
Get-Content "memo.txt"
git status --short -- "memo.txt"
git status --short
```

`--staged` はステージングエリア、`--worktree` は実ファイルを戻す指定です。`HEAD` に対象ファイルがあれば、両方がその内容に揃います。他のファイルの変更や、コミット履歴は変わりません。

`git restore --staged -- "memo.txt"` **だけでは、実ファイルは戻りません。** 削除のステージングが取り消され、表示が `D ` から ` D` に変わるだけです。

この例は `HEAD` の版を戻す方法です。削除前にコミットしていなかった新しい編集を回収する方法ではありません。

## コミット済み：ファイルが残っている版から取り出す

削除をコミットした後は、`HEAD` 自体に対象ファイルがありません。まず、そのファイルを削除したコミットを探します。

```powershell
git log --oneline --diff-filter=D -- "memo.txt"
```

`D` は削除の変更に絞る指定です。履歴に複数の削除があれば、日時や内容を確認して、今回戻したい削除を選びます。

以下のハッシュは例です。**実際に表示された削除コミットのハッシュに置き換えてから**実行します。

```powershell
$deletedCommit = "f9b37d4"
git show --stat $deletedCommit
git show "${deletedCommit}^:memo.txt"
```

`^` は指定コミットの最初の親を表します。通常の削除コミットなら、その親が「削除直前の版」です。2つ目のコマンドで、そこでのファイル内容を読めます。

この読み取りに失敗したら、まだ復元しません。パスやコミットの選択を見直します。名前変更・移動やマージが絡む履歴では、単純に親を選ぶだけでは欲しい版にならないことがあります。ここでは通常の削除コミットを扱います。

内容が目的の版であることを確認したら、1ファイルだけ取り出します。

```powershell
git restore --source="${deletedCommit}^" -- "memo.txt"
Test-Path "memo.txt"
Get-Content "memo.txt"
git status --short
```

この操作は**過去の内容を作業ツリーに置くだけ**です。ブランチを過去に戻したり、削除コミットを消したりはしません。現在のコミットで存在しないファイルを戻した場合は、通常 `?? memo.txt`（未追跡）になります。

その後、復元を新しい変更として記録します。

```powershell
git add -- "memo.txt"
git diff --staged
```

add後の表示は `A  memo.txt` です。**ここで止まり、`git diff --staged` でコミットに含まれる変更全体を確認してください。** 対象ファイルだけaddしても、別の変更がすでにステージされていれば、その変更も次のコミットに含まれます。復元分だけを記録したいなら、別の作業を先に別コミットへ保存するか、該当ファイルのステージングを `git restore --staged -- "別ファイルのパス"` で取り消します。この指定ではその別ファイルの編集内容は残ります。

意図した復元分だけがコミット対象になっていることを確認してから、記録します。

```powershell
git commit -m "削除したmemo.txtを復元"
git show --stat HEAD
git status --short
```

対象を絞った `restore` では、別ファイルのステージ済み・未ステージの変更は維持されます。また、削除コミットに含まれていた別の意図的な変更も、そのまま残せます。

## push済み：復元を新しい変更として共有する

push済みかどうかは、ファイルの `status` だけでは分かりません。共有先が `origin` の場合、最新情報を取得し、削除コミットを含むリモート追跡ブランチを確認します。前節で選んだ `$deletedCommit` を使います。

```powershell
git fetch origin
git branch -r --contains $deletedCommit
```

例えば目的の `origin/main` が表示されたら、取得時点のそのブランチの履歴に削除コミットが含まれています。表示がない場合も、別の共有先に送った可能性は残るので、リモートとブランチを確認してください。

復元方法は前節と同じです。ファイルを取り出し、新しいコミットを作った後、通常のpushで共有します。上流ブランチを設定済みの作業ブランチなら、次を使えます。

```powershell
git push
```

保護された共有ブランチにいる場合は、復元前にプロジェクトのルールに沿って作業ブランチを作ります。適切な起点のブランチにいることを確認してから、例えば `git switch -c fix/restore-memo` で作成します。初回pushは `git push -u origin fix/restore-memo` とし、Pull Requestで取り込みます。通常のpushが、そのままPRの作成やマージになるわけではありません。

pushが成功したら、共有先の**送信した作業ブランチ**でファイルを確認します。例えば `fix/restore-memo` に送った場合は、次で最新情報を取得して内容を読めます。別の名前で送った場合はブランチ名も置き換えます。

```powershell
git fetch origin
git show "origin/fix/restore-memo:memo.txt"
```

削除コミットと復元コミットが両方残るので、「削除した後に戻した」経緯も分かります。共有済みの履歴を巻き戻す操作や、force pushは不要です。

### 削除コミット全体を取り消したい場合だけrevertを使う

`git revert` は、指定コミットの変更を打ち消す**新しいコミット**を作ります。対象が「ファイル削除＋別ファイルの編集」なら、その編集も取り消します。

| 戻したい範囲 | 選ぶ操作 |
| --- | --- |
| `memo.txt` だけ戻し、他の変更は残す | `git restore --source=... -- "memo.txt"` → add → commit |
| 削除コミットに含まれる変更を全部取り消す | `git revert` |

revertする前には、`git status --short` が空であることと、`git show` で対象コミットの全変更を確認します。未コミットの作業があるなら、先に保存・整理します。

```powershell
git status --short
git show $deletedCommit
```

未コミットの変更がなく、表示されたコミットの変更を**すべて取り消してよい**と確認できた場合にだけ、次へ進みます。

```powershell
git revert --no-edit $deletedCommit
```

エラーや競合が出たら、ここで止まって次の段落の対処を確認します。成功した場合は、内容と取り消しコミットを確認します。

```powershell
Get-Content "memo.txt"
git show --stat HEAD
git log --oneline -3
git status --short
```

成功したら、できた取り消しコミットを作業ブランチから通常のpushまたはPRで共有します。後続コミットまで丸ごと巻き戻す操作ではありません。ただし、後の変更とぶつかると競合することがあります。

競合した場合は、後続のpushへ進まず `git status` を確認します。解消方法が分からず中止するなら、次でrevert開始前の状態に戻せます。

```powershell
git revert --abort
```

マージコミットのrevertには別の判断が必要です。この例の対象には含めません。

## Gitで戻せる範囲と、確認した検証結果

Gitは「記録した版」を戻す道具です。**一度もadd・commit・stashなどで保存していないファイルや編集内容は、Gitから復元できません。** ファイルが戻っても、消す直前に書いた未保存の編集まで戻ったとは限らないので、中身を確認します。

Gitにない内容は、Windowsのごみ箱、エディタのローカル履歴、バックアップなどを確認します。削除方法によってはごみ箱にも入りません。addしたことがあっても、ステージングエリアから削除済みなら、ここで紹介した手順で必ず回収できるとは限りません。

以下は、記事制作時にAIが**Linux / Git 2.51.1**の新しい一時リポジトリで実行した結果です。push先はローカルのbareリポジトリです。Windows・PowerShellで実行した結果ではありません。上のコード例はWindowsの読者向けに表記しています。

| 検証した状況 | 実行結果 |
| --- | --- |
| 未ステージの削除 | 保存済みの内容が戻り、別ファイルの未コミットの編集は残った |
| ステージ済みの削除 | `--staged` だけでは実ファイルが戻らず、`--worktree` を併用すると戻った |
| add済みの編集後に実ファイルを削除 | `restore` でadd済みの版が戻り、ステージ済みの編集も維持された |
| 削除をコミットした後、1ファイルだけ復元 | `??` → add後は `A `。別ファイルのステージ済み・未ステージの変更は残った |
| push済みの削除をrestore＋commitで復元 | 通常のpushが成功し、共有先にも復元内容が入った |
| 複数の変更を含むpush済みコミットをrevert | そのコミットの別ファイル編集も取り消され、後続の無関係なコミットは残った |
| 再追加とぶつかるrevert | 競合し、`--abort` で開始前の内容・履歴・状態に戻った |
| 一度もaddしていない新規ファイルを削除 | `restore` はエラーになり、回収できなかった |
| addしていない編集後にファイルを削除 | 記録済みの古い版は戻ったが、新しい編集は戻らなかった |

復元後は、**ファイルの存在、中身、`git status`、新しく作ったコミットの差分**を確認します。pushした場合は共有先の作業ブランチでも内容を確認すると、手元だけ戻った状態を見落とさずに済みます。
