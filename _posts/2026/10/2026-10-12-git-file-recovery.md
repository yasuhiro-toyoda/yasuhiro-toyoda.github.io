Gitで管理していたファイルを誤って消しても、記録が残っていれば戻せます。**まず `git status` で削除の状態を確かめます。未ステージの削除はステージから、ステージ済みの削除は最新コミット（`HEAD`）から、コミット済みの削除は削除前のコミットから戻す**のが基本です。

push済みでも、過去の履歴を消す必要はありません。復元を新しいコミットとして追加できます。ただし、Gitに一度も記録されていない内容まで戻せるわけではありません。

この記事は、add・commit・pushを使い始めた方向けの具体的な復元手順です。普段の操作は[Gitの基本的なコマンド]({% post_url 2026/05/2026-05-06-Gitの基本的なコマンド %})で確認できます。

## 最初に状態を確認する

Windows 11のPowerShellなどで、対象リポジトリの一番上のフォルダーを開きます。以下の `notes.txt` は例なので、**実際のファイルの相対パスに置き換えてください**。たとえば `docs/notes.txt` です。空白を含むパスも扱えるよう、引用符で囲みます。

```powershell
git --version
git status
git status --short
git diff -- "notes.txt"
git diff --staged -- "notes.txt"
```

`git restore` はGit 2.23以降のコマンドです。`--` は「ここから先はファイルの指定」という区切りです。

> **ほかの作業を守るために**
>
> 先に `git status` 全体と差分を読み、残したい未コミットのファイルはリポジトリの外へコピーしておきます。復元先に同名のファイルを作り直していたら、その内容も退避してください。対象パスの内容は復元元で置き換わります。この記事では、範囲の広い `git restore .` や `git reset --hard` は使いません。
{: .callout .callout--warning }

Gitには、手元のファイルがある「作業ツリー」、次のコミットに入れる内容を置く「ステージ（インデックス）」、保存済みの「コミット」があります。`HEAD` は、通常、今いるブランチの先頭コミットを指します。

`git status --short` の先頭2文字は、通常は**左がステージ、右が作業ツリー**の状態です。空白も意味を持ちます。

```text
 D notes.txt   ← 右側のD：削除は未ステージ
D  notes.txt   ← 左側のD：削除はステージ済み
MD notes.txt   ← 編集をステージした後、手元で削除した状態
```

この3行は別々の状態の例で、矢印以降は説明です。長い形式の `git status` では、未ステージの削除は `Changes not staged for commit`、ステージ済みの削除は `Changes to be committed` の欄に出ます。表示言語が日本語の場合もあります。[状態表示の仕様](https://git-scm.com/docs/git-status)

| 確認できた状態 | 進む手順 |
| --- | --- |
| ` D`、または編集をステージした後の `MD` | 次の「未ステージの削除を戻す」 |
| `D ` | 「ステージ済みの削除を戻す」 |
| 削除がstatusに出ないが、履歴にはある | 「コミット済みの削除から、1ファイルだけ戻す」 |
| 削除コミットが共有先にも含まれている | 同じ復元方法を使い、新しいコミットを通常の方法で共有する |

**statusに出ないことだけでは、コミット済みともpush済みとも断定できません。** 未追跡のファイルを消した場合や、別のブランチ・フォルダーを見ている場合もあります。履歴の探し方は後述します。

`UU`・`UD`・`DU`などの競合表示や、マージ・rebaseの途中という案内が出ている場合は、この表をそのまま適用せず、進行中の操作を先に確認してください。

## 未ステージの削除を戻す

削除が右側の `D` なら、ステージにはファイルが残っています。

```powershell
git restore -- "notes.txt"
git status --short
```

これで、**ステージにある内容が作業ツリーに戻ります**。削除前に編集をステージしていなければ、通常は最後にコミットした内容です。エディタでファイルを開き、必要な内容が戻ったか確認します。

- ` D notes.txt` だけだった場合：対象の表示が消えるのが通常です
- `MD notes.txt` だった場合：ステージ済みの編集が戻り、`M  notes.txt` が残ります。その編集を消したわけではありません
- 別のファイルにあった変更：そのまま残ります。status全体でも確認します

削除前に編集していても、その編集をaddしていなければ、`restore` はその未記録の編集までは再現できません。[復元元と復元先の仕様](https://git-scm.com/docs/git-restore)

## ステージ済みの削除を戻す

`git rm` を実行した場合や、削除した後に `git add` した場合は、左側に `D` が出ます。ステージからもファイルが消えているため、先ほどの `git restore` だけでは戻せません。

対象ファイルが最新コミットに存在する通常のケースでは、次の2段階で戻します。

```powershell
git restore --staged -- "notes.txt"
git status --short
git restore -- "notes.txt"
git status --short
```

1. `--staged` で、ステージを `HEAD` の内容に戻す。この時点では手元のファイルはまだなく、` D notes.txt` になる
2. そのステージから作業ツリーへ戻す。エディタで中身も確認する

対象にほかの変更がなければ、そのファイルの表示は消えます。この操作はコミットを追加せず、削除を取り消します。

> **削除前の未コミット編集には注意**
>
> この手順で戻すのは最新コミットの内容です。以前addした編集があっても、その後「削除」をステージすると、現在のステージは削除状態に置き換わっています。その編集の復旧は、この2行だけでは保証できません。
{: .callout .callout--caution }

## コミット済みの削除から、1ファイルだけ戻す

削除をコミットした後は、作業ツリーもステージも「ファイルがない状態」で一致します。そのため、statusがきれいでも不思議ではありません。

### 削除したコミットと、その直前を探す

まず、対象パスの削除履歴を見ます。

```powershell
git log --oneline --diff-filter=D -- "notes.txt"
```

たとえば `a1b2c3d Delete notes` と出たとします。**`a1b2c3d` は説明用のIDです。以下では、自分の結果に出た削除コミットのIDに置き換えてください。**

```powershell
git show --stat a1b2c3d
git show "a1b2c3d^:notes.txt"
```

最初の行で、そのコミットがほかのファイルも変更していないかを確認します。次の行は、削除コミットの直前にあった `notes.txt` の内容を表示するだけです。`^` は最初の親コミットを意味します。[履歴の絞り込み](https://git-scm.com/docs/git-log)、[コミットの指定方法](https://git-scm.com/docs/gitrevisions)

ここでは、親が1つの通常の削除コミットを想定しています。マージコミット、名前変更、履歴の浅いclone、別ブランチでの削除などで見つからない場合は、結果を決めつけず、ファイルが確実に存在したコミットと当時のパスを確認してください。`^` を付ければ常に目的の版になるわけではありません。

### 必要な内容を取り出して、新しいコミットにする

表示された内容が戻したい版なら、同じコミットを復元元にします。

```powershell
git restore --source="a1b2c3d^" -- "notes.txt"
git status --short
```

これは**今のブランチを過去へ巻き戻す操作ではありません**。指定した過去の版から、そのパスを作業ツリーへ取り出す操作です。ステージは変更しません。

現在のコミットとステージに対象ファイルがなければ、通常は `?? notes.txt` と出ます。復元できたファイルが「まだコミット対象になっていない」状態なので、異常ではありません。エディタで内容を確認してから、対象だけをaddします。

```powershell
git add -- "notes.txt"
git diff --staged -- "notes.txt"
git diff --staged --name-status
```

最後の行は、**今回のコミットに入るファイル全体**の確認です。`git commit` は、直前のaddだけでなくステージ済みの変更すべてを記録します。関係のない変更が表示されたら、そのままコミットせず、別の作業として保存するなどして分けてください。

復元するファイルだけがステージされていれば、記録します。

```powershell
git commit -m "Restore notes.txt"
git status
git log --oneline -3
```

元の削除コミットを残したまま、復元のコミットが増えます。削除と同じコミットで行われた別ファイルの修正は、この方法では取り消しません。

## push済みか確認し、共有先にも復元を届ける

**コミット済みとpush済みは別です。** `git status` のahead表示は、設定された追跡先との比較にすぎず、削除コミットが共有先にあるかを単独では証明しません。

まず前節の `git log` で削除コミットのIDを調べます。以下の `a1b2c3d` も、そのIDに置き換えてください。共有先の名前が `origin` の例では、復元・共有に進む前に次を実行します。共有先が違う場合は、その名前に置き換えます。

```powershell
git remote -v
git fetch origin
git branch -r --contains a1b2c3d
```

`fetch` は共有先の情報を取得します。作業ファイルへ変更を統合する `pull` とは異なります。最後の行に、たとえば `origin/main` が出れば、**手元に保存されたその共有ブランチの追跡履歴に、削除コミットが含まれています**。[fetchの仕様](https://git-scm.com/docs/git-fetch)、[containsの仕様](https://git-scm.com/docs/git-branch)

ただし、通常のfetchでは削除済みの共有ブランチの追跡情報が残る場合があり、別remoteの情報も今回更新したとは限りません。表示は共有された証拠として扱い、現在の送信先の状態はGitHubやGiteaの画面でも確認します。

何も出なくても「一度も共有していない」とは断定できません。取得対象外のブランチや別remote、削除済みの共有ブランチなどは、この確認から漏れます。fetchが失敗した場合も最新の共有状態は未確認です。分からなければ共有済みとして扱い、履歴を書き換えない方法を選びます。

push済みでも、前節の「ファイルを取り出す→add→commit」は同じです。復元コミットを、いつもの作業ブランチからpushし、PRが必要なリポジトリではPRで共有します。

```powershell
git push
```

この1行は、いつものpush先が設定されている前提です。送信先が不明なら実行せず、ブランチと運用ルールを確認してください。拒否された場合もforce pushはせず、リモート側の更新や保護ルールを確認します。

pushが成功したら、GitHubやGiteaの**送信先ブランチ**で、復元コミットとファイル内容を確認します。PRを使う場合は、作業ブランチへのpushと共有ブランチへの反映は別の段階です。

## 削除コミット全体を取り消したい場合はrevert

1ファイルを取り出す `restore` と、コミットの変更を打ち消す `revert` は、影響範囲が違います。

| 方法 | 対象 | 履歴への反映 |
| --- | --- | --- |
| `restore --source=… -- "notes.txt"` | 指定したパスの内容 | 確認後、自分でadd・commitする |
| `revert コミットID` | 指定したコミットの変更全体 | 打ち消す新しいコミットを作る |

削除コミットに必要な別の修正も入っているなら、前節までの対象ファイルだけの復元が向いています。**そのコミット全体が不要**な場合だけ、次の手順を検討します。

まず、未コミットの作業は別の適切なコミットなどに保存し、`git status` がcleanであることを確認してください。残したい未追跡ファイルも退避します。

```powershell
git status
git show a1b2c3d
git revert --no-edit a1b2c3d
```

`git show` の差分全体を読んでからrevertします。`--no-edit` はコミットメッセージの編集画面を開かない指定です。単にファイルが戻るだけでなく、同じコミットに含まれる別の変更も打ち消されます。共有済みでも元の履歴は残ります。[revertの仕様](https://git-scm.com/docs/git-revert)

競合した場合、復元完了ではありません。初心者のうちは、内容を判断できないまま続行せず、次で今回のrevertを中止できます。

```powershell
git revert --abort
```

正常終了後は、対象の中身、`git status`、`git show --stat HEAD` を確認します。共有が必要なら、先ほどと同じ通常のpush・PRの流れに進みます。マージコミットのrevertは別途判断が必要なので、ここでは扱いません。

## Gitに記録されていない内容は戻せないことがある

復元できるのは、Gitが保持している内容です。

- 一度もadd・commitしていない新規ファイル：この手順では復元できません
- コミット後に編集し、addせず削除した内容：最後の記録済みの版は戻せても、その編集分は戻りません
- 編集をaddした後、削除はまだaddしていない：現在のステージの内容から戻せます（`MD` の例）
- 過去にaddしただけで、現在のステージにも残っていない内容：内部にデータが残る場合はありますが、この手順での復元や保存期間は保証できません

Windowsのごみ箱、エディタのローカル履歴、OneDriveなどの版履歴やバックアップも確認先になります。ただし、使った削除方法や設定によって残り方が違います。Gitで戻らないからといって、むやみに削除・クリーンアップを重ねないようにします。

最後は「コマンドがエラーなく終わったか」だけでなく、**ファイルの内容、status、コミット履歴、必要なら共有先**の4点で確認しましょう。
